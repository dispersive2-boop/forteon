# Правила работы с репозиторием ForteOn

Документ для всех, кто вносит изменения. Цель — чтобы история читалась как журнал решений,
а не как свалка «fix», и чтобы любой коммит можно было откатить по отдельности.

---

## 1. Ветки

Схема простая (упрощённый Git Flow), рассчитана на небольшую команду:

| Ветка | Назначение | Кто коммитит | Защита |
|---|---|---|---|
| `main` | то, что развёрнуто на `forteon.pro`; всегда работоспособно | только через merge PR | push запрещён, history не переписывается |
| `develop` | интеграция готовых фич перед релизом | только через merge PR | push запрещён |
| `feature/<кратко>` | одна задача / один пункт ТЗ | автор | — |
| `fix/<кратко>` | исправление дефекта | автор | — |
| `chore/<кратко>` | инфраструктура, зависимости, CI | автор | — |
| `docs/<кратко>` | только документация | автор | — |

Правила:

- Ветка живёт **не дольше одной задачи**. Слили — удалили.
- Ответвление **всегда от `develop`**, не от `main`.
- Перед PR: `git fetch && git rebase origin/develop` — линейная история без «Merge branch develop».
- Имя ветки — латиницей, через дефис, по сути изменения:
  `feature/task-chat-notes`, `fix/duplicate-tasks`, `chore/git-setup`.

## 2. Коммиты

Формат — [Conventional Commits](https://www.conventionalcommits.org/):

```
<тип>(<область>): <что сделано, до 72 символов>

Почему это сделано и что это лечит. Если есть номер пункта ТЗ — указать.
Побочные эффекты, миграции данных, ручные шаги.

Refs: #12
```

Типы: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `perf`, `build`, `ci`.
Области: `planner`, `notes`, `tasks`, `clients`, `finance`, `ai`, `db`, `api`, `ui`, `tests`, `deploy`.

Хорошо:

```
fix(tasks): не ставить «Уточнить» задачам без срока

needs_review выставлялся по условию due_date is null, из-за чего 270
импортированных задач из Excel выглядели как ошибки разбора.
Теперь флаг ставит только классификатор событий при реальной
неоднозначности (п.3, п.12 ТЗ).

Refs: #7
```

Плохо: `fix`, `update`, `правки`, `работает`.

Один коммит = одно логическое изменение. Не смешивать рефакторинг и поведение.
Настроить шаблон сообщения: `git config commit.template .gitmessage`.

## 3. Что нельзя коммитить

Уже закрыто в [`.gitignore`](.gitignore), но проверяйте `git diff --cached` перед коммитом:

- `.env`, `.env.local` — только [`.env.example`](.env.example) с пустыми секретами;
- `*.db`, `*.db-wal`, `*.db-shm`, `backend/_backup/` — боевые данные и снимки;
- `node_modules/`, `.next/`, `__pycache__/`;
- одноразовые скрипты `_*.py` — они живут на диске, но не в истории.

Если секрет всё же улетел в коммит — недостаточно удалить файл следующим коммитом:
значение нужно **отозвать и заменить**, а историю чистить (`git filter-repo`).

## 4. Проверки перед PR

Локально обязательно обе команды должны быть зелёными:

```bat
cd backend && python -m pytest tests -q
cd frontend && node node_modules/typescript/bin/tsc --noEmit
```

Плюс, если менялось поведение — сквозная проверка на живом API
(`backend/_verify_*.py`), а не только «HTTP 200».

Тесты используют изолированную БД из [`backend/tests/conftest.py`](backend/tests/conftest.py)
и **не касаются боевой**. Если тест лезет в `backend/data/forteon.db` — это дефект теста.

## 5. Pull request

- Заголовок — по той же схеме, что и коммит.
- В описании: что было не так, что изменилось, как проверено (команды и результат),
  скриншоты для UI-изменений.
- Мерж — **squash** в `develop`, чтобы одна фича = один коммит в интеграционной ветке.
- Релиз: `develop` → `main` отдельным merge-коммитом с версией (`v1.2.0`),
  затем тег `git tag -a v1.2.0 -m "..."`.
- Ветку удалять сразу после мержа.

## 6. Миграции данных

Изменения, которые правят боевые записи (чистка дублей, пересчёт флагов),
оформляются отдельным скриптом с обязательным:

1. снимком БД перед запуском (`sqlite3` backup API, не копирование файла при WAL);
2. режимом сухого прогона по умолчанию (`--apply` для записи);
3. отчётом «сколько строк затронуто» до и после.

Образец — [`backend/_fix_duplicates.py`](backend/_fix_duplicates.py).

## 7. Версии и теги

- `main` всегда имеет тег последнего релиза.
- Нумерация — семантическая: `MAJOR.MINOR.PATCH`.
- В `CHANGELOG.md` (если появится) — только то, что видит пользователь.
